## Feature 1: End-to-End Pipeline Orchestrator

### Feasibility: 7/10

**Justification:** An orchestrator already exists at `orchestrator.py` (1,086 lines). It imports all 8 engines, runs an 11-stage pipeline with CLI flags, error handling, email notifications, webhook delivery, and state persistence to `outputs/pipeline_state.json`. This is not a greenfield build -- it is an enhancement of existing code.

### Technical Complexity

**What is being overestimated:** The scope of "building" an orchestrator. The `BDOrchestrator` class already exists with `run_full_pipeline()` that chains all engines sequentially. The fundamental wiring is done.

**What is being underestimated:**
- **Checkpointed resume.** The current `_save_pipeline_state()` saves results after completion but has no mid-pipeline checkpointing. If the pipeline crashes at stage 7 of 11 after processing 80 jobs through LLM-based standardization (which costs real API dollars), there is no way to resume from stage 7. This requires a proper state machine with per-stage persistence, per-job tracking, and idempotent re-entry.
- **Batch processing at 100+ scale.** The Engine2 pipeline processes jobs sequentially. Each job makes a Claude API call for LLM extraction. At 100+ jobs, this means 100+ synchronous API calls with no parallelism, no rate limiting, and no backpressure.
- **Engine interface heterogeneity.** Each engine has a different calling convention. Some return dataclasses, some return dicts, some mutate in-place.

### Dependencies & Blockers

- **Hidden dependency: Embedding dimension mismatch.** `phase7_endpoints.py` line 444 still creates collections with `size=384` while the vector store uses `EMBEDDING_DIMENSION = 1536`.
- **Engine 6 (QA) is incomplete.** Marked as "in progress" in CLAUDE.md.
- **Engine 1 (Scraper) is external (Apify).** The orchestrator assumes input data already exists.

### Risk Analysis

| Risk | Probability | Impact | Mitigation |
|------|------------|--------|------------|
| LLM API failures mid-batch crash entire run | High | High | Implement per-job checkpointing with SQLite state store |
| 100+ job batch takes >1hr, times out | Medium | High | Add asyncio parallelism with configurable concurrency |
| Engine 6 QA module fails at runtime | Medium | Medium | Graceful fallback already exists (try/except), but test it |
| Re-indexing Knowledge on stale embeddings | High | High | Fix embedding dimensions BEFORE wiring orchestrator to Engine 8 |

### Effort: L (Large)

### Quick Wins
1. Run the existing `orchestrator.py --input ... --test` with 3 jobs to identify which engines actually load vs. fail at import time.
2. Add `--resume` flag that reads `pipeline_state.json` and skips completed stages.
3. Add `batch_size` chunking to the main loop so 100 jobs are processed in groups of 10.

## Feature 2: Dashboard Live API Integration

### Feasibility: 6/10

**Justification:** Partial wiring already exists. The dashboard has `useAppData.ts` using TanStack Query that tries the Hub API first, then falls back to local JSON. The API has 120+ route handlers. However, 48 dashboard pages exist and most still use static JSON.

### Technical Complexity

**Underestimated:**
- Schema mismatch between static JSON and API responses
- Missing API endpoints for specialized views (EnrichmentDashboard, CompetitiveLandscape, etc.)
- Error boundaries and loading states for 48 pages

### Dependencies & Blockers
- API must be running and stable
- Feature 3 (Auth) will force a second migration pass if not designed for from the start
- CORS configuration needed

### Effort: L (Large)

### Quick Wins
1. Audit which pages use `useData()` vs `useAppData()` and create a migration checklist.
2. Migrate the 5-6 most-used pages first (Contacts, Programs, JobsPipeline, Analytics, PipelineStatus).
3. Build a shared `apiClient.ts` with error handling, retry, and auth header injection.

## Feature 3: API Authentication & Security Layer

### Feasibility: 5/10

**Justification:** Currently ZERO authentication on 120+ API endpoints that serve defense intelligence data. This is a serious security gap.

### Technical Complexity

**Massively underestimated:**
- The API is monolithic: 120 `@app.get/post` decorators plus 20+ sub-routers
- No user database, user model, or password storage exists
- RBAC granularity requires a policy document that does not exist
- JWT requires full infrastructure: user database, password hashing, token generation, refresh tokens, token blacklist

### Effort: XL (Extra Large)

### Quick Wins
1. Add a simple API key middleware (`X-API-Key` header check) as interim measure -- 20 lines of code.
2. Define the RBAC policy document before writing code.
3. Use FastAPI's `Security` dependency pattern for router-level auth.
