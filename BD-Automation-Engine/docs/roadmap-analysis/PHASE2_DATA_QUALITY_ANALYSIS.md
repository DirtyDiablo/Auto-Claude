## Feature 7: SAM.gov Federal Opportunity API Integration

### Feasibility: 7/10

A working `SAMGovSync` class already exists at `Engine8_Knowledge/scrapers/sam_gov_sync.py` with data models, watch management, and both Tango API and SAM.gov API request methods using `httpx` async clients. The dual-API approach (Tango primary, SAM.gov free fallback) is architecturally sound. However, the scraper is "disabled" -- authentication flow, pagination, and rate limiting are not battle-tested.

### Key Risks
- SAM.gov API key registration takes 2-4 weeks -- **apply NOW**
- Rate limits are aggressive (10 requests/min free tier)
- Cross-referencing with 388 federal programs requires entity resolution across inconsistent naming conventions
- Embedding dimension mismatch must be resolved first

### Revenue Impact: HIGH
Direct pipeline to ~$950M DCGS portfolio. Catching a recompete opportunity 30 days earlier has quantifiable value.

### Effort: L (Large)

## Feature 8: QA Human Review Queue Dashboard

### Feasibility: 8/10

The backend is surprisingly complete. `Engine6_QA/scripts/qa_feedback.py` already has:
- `ReviewQueue` class with JSON persistence
- `evaluate_item()` with root cause analysis
- `QAStatus` enum (PENDING, APPROVED, NEEDS_REVIEW, REJECTED)
- `RootCause` dataclass with issue types, severity levels, auto-fixable flags

The review queue JSON already contains **45+ real items** with root cause analysis, confidence scores, and review reasons -- all with `"reviewed": false`. Zero reviews processed since January 2026. This is the clearest signal that the human-in-the-loop workflow is broken at the UI layer.

### Key Risks
- Duplicate entries in review queue (same `job_id` appearing multiple times)
- JSON file persistence is a bottleneck and corruption risk at scale
- Feedback loop to scoring algorithm requires outcome data collection mechanism

### Revenue Impact: MEDIUM-HIGH
Uncaught misclassifications erode BD team trust. Every incorrectly mapped contact is a missed revenue opportunity.

### Effort: M (Medium) -- backend 80% done

## Feature 9: Real-Time Notion & Bullhorn Sync

### Feasibility: 5/10 -- RISKIEST FEATURE IN PHASE 2

**CRITICAL: Notion has NO webhook support.** The only way to detect changes is polling via `databases.query` with `last_edited_time` filter. For 8 databases at Notion's 3 req/sec rate limit, achieving "2-5 minute" sync is barely feasible.

**Bullhorn OAuth is incomplete.** The `BullhornClient` in `bullhorn_integration.py` has the OAuth flow stubbed (line 77: "Note: In production, this would be a proper OAuth flow").

### Recommendation: DESCOPE
Rename to "Improved Incremental Batch Sync" running every 15-30 minutes rather than daily. This reduces effort from XL to L and eliminates conflict resolution complexity.

### Key Risks
- Notion lacks webhooks -- certain blocker for "real-time"
- Bullhorn Enterprise subscription may be required
- Conflict resolution for 44,745 candidates is non-trivial
- 293MB SQLite file is architecturally incoherent for "real-time" -- need Bullhorn API polling

### Revenue Impact: MEDIUM -- faster sync helps but current batch model works

### Effort: XL (Extra Large) as stated, L if descoped

## Feature 10: NER-Powered Entity Enrichment Pipeline

### Feasibility: 8/10 -- LOWEST HANGING FRUIT

The `DefenseNER` class at `Engine8_Knowledge/ml/defense_ner.py` already has:
- 10 custom entity types: PROGRAM, CONTRACT, COMPANY, INSTALLATION, CLEARANCE, NAICS, ROLE_TITLE, SET_ASIDE, AGENCY, VALUE
- Pattern-based extraction that **works today** without training
- spaCy model loading with blank model fallback
- Deduplication logic

The training stub is a no-op (sets `_trained = True` without actual training), but pattern-based extraction is immediately useful for reducing Claude API costs.

### Key Risks
- Low risk overall
- Pattern-based matching misses company name variations ("GDIT" vs "General Dynamics IT")
- Integration into Engine 2/3 requires modifying `job_standardizer.py` and `contact_classifier.py`

### Revenue Impact: MEDIUM (compound)
Better entity extraction improves program mapping accuracy → improves BD scores → improves call list quality → improves conversion rates. Estimated 15-25% reduction in false positive program mappings.

### Effort: M (Medium)

## Feature 11: BD Score Validation & Calibration

### Feasibility: 6/10

The calibration mechanism exists in code. `bd_scoring.py` contains a complete `recalibrate()` function (lines 369-543) that adjusts factor weights based on actual success rates with a configurable learning rate.

### Critical Problem: Cold Start
There is **no outcome data** to calibrate against. The function expects conversion data with outcomes (placement, meeting, response, no_response) but no mechanism exists to capture whether scored contacts resulted in actual placements. Federal BD cycles are 6-18 months.

### Workaround
- Use intermediate signals (meeting booked, response received) as proxies
- Use the 2,202 existing Bullhorn placements as historical validation data
- Require minimum 100+ tracked outcomes before calibration activates

### Effort: L (Large) -- not for the algorithm (already done) but for data infrastructure
